把身分擋在 Agent 前面

一道登入閘門,怎麼串起來

▶ 看影片 🎓 企業落地與找痛點 🎬 9 個段落 🀄 投影片 + 逐字稿
本集開場

先問你一個問題。你花了很大力氣,做了一個很聰明的 agent,它能查你公司的內部文件、能回答很專業的問題。然後你把它放上線 —— 這時候第一個撞到的,不是模型夠不夠強,是**誰可以問它**?它答出來的內部資料,**憑什麼給這個人看**?這一集,我們就把這道最容易被跳過、卻最先爆炸的關卡,從頭到尾串一遍。

1

現實:agent 一上線,就是門大開

🚪
  • 1它能查內部知識,也就能被任何人問
  • 2沒有身分這關,等於把資料室的門拆了
  • 3模型越強,漏出去的風險越大
逐字稿

很多人做 agent,focus 全在模型跟知識庫,做完直接開一個網址、或一個 API 就上線了。問題是:這個 agent 能查的是你的內部知識,也就代表 —— **任何拿到這個網址的人,都能問到那些內部知識**。你等於把資料室的門整個拆掉,只留一個很聰明的管理員站在那,但他不會問你是誰、有沒有資格進來。而且很殘酷的是:你的模型越強、知識庫越完整,這個門大開的風險就越大,不是越小。

2

真正的問題,不是模型,是身分

❓
  • 1不是「怎麼讓它答得更好」
  • 2而是「誰能問、憑什麼給他看」
  • 3身分是入場券,不是加分項
逐字稿

所以問題要換個問法。不是「我怎麼讓這個 agent 答得更準」,而是「**誰**能問這個 agent,而它答出來的東西,**憑什麼**給這個人看」。身分這件事,不是等你上線很久、出事了才回頭補的加分項,它是**入場券** —— 沒有它,後面所有的聰明都是裸奔。把問題換成這樣問,你就會發現:模型只是後面那一段,前面必須先有一道關卡,先確認「你是誰」。

3

答案:中間放一個「守門 + 代打」

🧱
  • 1不改 agent、不改身分系統,在中間加一層
  • 2它負責:先驗身分,再替你去打後端
  • 3術語叫 BFF —— 前端的後端
逐字稿

答案是:agent 不改、公司的身分系統也不改,在它們**中間**放一層。這一層做兩件事:第一,使用者要先在它這裡通過身分驗證;第二,驗過之後,是**它**替使用者去打後面的 agent,不是使用者直接打。這個模式有個名字叫 BFF —— **前端的後端**。你可以把它想成一個櫃檯:客人不能自己衝進辦公室,要先在櫃檯出示證件,櫃檯確認沒問題,才幫你把事情轉進去。重點是,這個櫃檯是**新加的一層**,前面的網頁、後面的 agent、旁邊的身分系統,一個都不用動。

4

整條路長這樣(循序圖)

🗺️
逐字稿

我們把整條路走一遍。使用者打開一個很乾淨的網頁,點登入;中間這層就把他導去身分提供者的登入頁,他輸入帳密登入;登入完,身分提供者會發一個**授權碼**回到中間層;中間層拿這個碼,在**後端**換成一張身分 token —— 注意,換 token 用到的**密鑰,從頭到尾只在後端**,使用者的瀏覽器碰不到。換好之後,把 token 交回網頁。接下來使用者每次問問題,都帶著這張 token;中間層先驗這張 token 有沒有效 —— 有效,才**代替他**去打後面的 agent、把有憑有據的答案帶回來;無效或根本沒登入,就直接擋下。

5

為什麼守門的是後端,不是瀏覽器

🛡️
  • 1換 token 的密鑰,只能放後端
  • 2放進瀏覽器 = 等於公開
  • 3所以身分系統那邊要登記成「機密用戶端」
逐字稿

這裡有個很多人會做錯的地方。換 token 這件事,需要一把**密鑰**。如果你圖方便,讓瀏覽器自己去換 token,那把密鑰就得放進瀏覽器 —— 而**放進瀏覽器的東西,等於公開**,任何人打開開發者工具都看得到。所以正確的做法是:換 token 這件事,發生在**中間層的後端**,密鑰只住在後端,瀏覽器只拿得到最後那張 token。對應到設定,就是你在身分系統那邊,要把這個應用登記成「機密用戶端」,而不是「純前端應用」。這一個選擇選錯,整個安全就破了。

6

怎麼證明閘門有效:反過來測

🚫
  • 1正路能通,不稀奇
  • 2沒帶身分直接打,要被擋成 401
  • 3被擋下來,才叫閘門真的存在
逐字稿

做完之後,怎麼證明這道閘門是真的有用?很多人只測「正路」—— 登入、問問題、有答案,好棒,上線。但真正該測的是**反路**:假設有人根本沒登入,直接對著你那個問答的網址硬打,它應該要**直接擋下來,回一個 401 未授權**,而不是傻傻地把答案吐出去。一個閘門,是靠它**擋得住不該進來的人**來證明存在的,不是靠它讓對的人通過。所以驗收的時候,一定要故意不帶身分打一次,看它有沒有擋。

7

順帶一個坑:名字叫「文件問答」不代表它查文件

📄
  • 1很多 RAG app,流程其實是「問題直接丟給模型」
  • 2沒有接知識庫那一步,答的是模型的常識
  • 3要真的接上檢索,答案才是你的資料
逐字稿

串到後面,我踩到一個很典型的坑,順便講給你聽。後端那個 agent,名字叫「內部文件問答」,聽起來理所當然會查文件對吧?結果我一問,它回我「我看不到你的文件內容」。去看它的流程才發現 —— **它根本沒有查知識庫那一步**,是把問題直接丟給大模型,用模型自己的常識在答。名字叫文件問答,不代表它真的接了你的文件。你要在流程裡明確加一個**知識檢索**的步驟、指到你的知識庫,再把檢索到的內容餵給模型,它答出來的**才是你的資料**。這一步沒接,前面身分驗證做得再漂亮,使用者拿到的還是罐頭答案。

8

這條線的大圖:一個身分,罩住所有系統

🌐
  • 1同一套身分,可以同時罩 ERP、罩 agent、罩 RAG
  • 2認證(你是誰)很好聯邦化、一套通吃
  • 3授權(你能看哪一級)才是下一道真正的牆
逐字稿

最後拉高一層看。這道閘門的價值,不只是保護這一個 agent。同一套身分,今天可以罩住你的 agent,明天可以用**一模一樣**的方式罩住你的 ERP、你的內部系統 —— 差別只在中間那層前面接的是誰。這就是「**身分集中、能力分散**」:把「你是誰」收斂到一個身分提供者,前面加一道守門的中間層,後面愛接什麼系統都行。但我要很誠實地跟你說:今天做的是**認證** —— 確認你是誰,這件事很好標準化、一套通吃。真正難的是下一道牆:**授權** —— 同一個登入的人,誰能看一般知識、誰能看機敏資料,那是每一家公司都不一樣、要自己設計的映射。認證好聯邦化,授權才是那道真正的牆。這一集,我們先把認證這道門立起來。

9

🗝️
逐字稿

收一句心法:**認證是入場券,授權才是那道牆。**你不需要為了替 agent 加身分,去重寫 agent、也不用去動公司的身分系統;你只需要在中間立一道守門的閘門,先確認「你是誰」,再替你去打後面。門立起來之後,後面要接第幾道授權、要不要分級,就是你可以慢慢長的事了。
